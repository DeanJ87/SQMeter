# Feature Specification: Settings backup and restore

**Feature Branch**: `feature/033-config-backup`

**Created**: 2026-10-18

**Status**: Draft

## Context

The only way to back up a SQMeter's settings today is `curl /api/config` (docs/user-guide/configuration.md,
"Backup & Restore"). That export masks every secret as `********`, so a backup restored onto the same
device keeps its passwords, but restored onto a replacement device (the usual reason to have a backup) it
brings no WiFi, MQTT, device or alert passwords at all. There is no button for it, no preview, and no
check that the file suits the board it is going onto, which matters now that SQMeter runs on several boards
(classic ESP32, ESP32-S3-ETH, ESP32-S3-Zero) with different pins.

This spec adds a Back up / Restore pair to the web UI. Settings stay readable in the file; secrets are
included only in encrypted form, protected by a passphrase the owner chooses, so they never leave the
device in clear text.

Out of scope: scheduled or automatic backups, cloud storage, backing up history, recent alerts or language
packs, and cloning a device's identity (its MAC-based client IDs are regenerated by each device).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Back up the settings (Priority: P1)

The owner opens Settings → Device, presses Back up settings, and downloads a file holding every setting.

**Why this priority**: without a backup there is nothing to restore.

**Independent Test**: press Back up settings without a passphrase; the file downloads, opens as readable
text, contains every settings section, and contains no secret.

**Acceptance Scenarios**:

1. **Given** Settings → Device, **When** the owner presses Back up settings without a passphrase, **Then**
   a file named after the device and date downloads, holding all settings (network, MQTT, sensors and
   calibration, sky sensors, display, battery, safety, alerts, Alpaca, BLE, language, location) and no
   secret values.
2. **Given** the owner enters a passphrase (twice), **When** they back up, **Then** the file also holds the
   secrets, encrypted, and the UI says the passphrase is needed to restore them and can't be recovered.
3. **Given** a device password is set, **When** someone without it requests a backup, **Then** it is
   refused.

---

### User Story 2 - Restore with a preview (Priority: P1)

The owner replaces a failed device, uploads the backup on the new one, sees what will change, and
confirms.

**Why this priority**: the reason backups exist.

**Independent Test**: restore a backup onto a device with different settings; the preview lists exactly
the differing settings; after confirming, the device's settings match the backup.

**Acceptance Scenarios**:

1. **Given** a backup file, **When** the owner uploads it, **Then** the device shows a preview grouped by
   section: each setting that will change with its current and new value, secrets only as "will change" /
   "unchanged", and nothing is applied yet.
2. **Given** the preview, **When** the owner confirms, **Then** the settings are applied as one save, and
   the device restarts only if a changed setting needs a restart (and says so before confirming).
3. **Given** the preview, **When** the owner cancels, **Then** nothing changes.

---

### User Story 3 - Secrets come back only with the passphrase (Priority: P1)

**Why this priority**: secrets are the part a plain export can't restore, and the part that must stay
protected.

**Independent Test**: restore an encrypted backup with the right passphrase and the secrets are restored;
with a wrong one, restore stops with nothing changed; without one, everything except secrets restores and
the device keeps its current secrets.

**Acceptance Scenarios**:

1. **Given** a backup with encrypted secrets and the right passphrase, **When** restored, **Then** the
   preview marks which secrets will change and confirming restores them.
2. **Given** a wrong passphrase, **When** the owner uploads, **Then** the device says the passphrase is
   wrong (without saying which secret failed), and nothing is changed.
3. **Given** a backup with encrypted secrets and no passphrase entered, **When** restored, **Then** the
   preview says secrets will be kept as they are on this device, and the rest restores.

---

### User Story 4 - Safe across boards and versions (Priority: P2)

The owner restores a backup from a classic ESP32 onto an ESP32-S3-Zero, or from an older firmware.

**Why this priority**: moving to the new boards is the main migration in v0.4.

**Independent Test**: restore a backup whose pins don't exist on this board; the preview flags those
settings and offers to keep this board's values; confirming applies everything else.

**Acceptance Scenarios**:

1. **Given** a backup from another board, **When** previewed, **Then** settings that can't apply here
   (pins not broken out, sensors or features this board lacks) are listed with the reason, and the owner
   can restore the rest while those keep this board's values.
2. **Given** a backup from older firmware, **When** previewed, **Then** settings it lacks keep their current
   values and the preview says so; **given** a backup from newer firmware, **Then** the preview warns and
   unknown settings are listed as ignored.
3. **Given** a file that isn't a SQMeter backup, or is damaged, **When** uploaded, **Then** it is refused
   with a clear reason and nothing changes.

### Edge Cases

- A backup made on the device it is restored to, unchanged: the preview says nothing will change.
- The restored WiFi network differs from the current one: the preview warns that the device will join the
  other network and may become unreachable at its current address, and explains how to get back (WiFi
  setup hotspot).
- The restored device password differs: the preview warns that the next page load will ask for the
  backup's password.
- Restoring while an imaging app is connected: the preview warns if the restart will interrupt it.
- Very large alert wording or many settings: the file stays well within the device's upload and saved
  settings limits; a file over the limit is refused before parsing.
- The passphrase is forgotten: the secrets in that file can't be recovered; the rest still restores.

## Clarifications

### Session 2026-10-18 (owner)

- Q: Should a backup include passwords and tokens? → A: Only encrypted: the owner sets a passphrase and the
  device encrypts the secrets with it; restoring them needs the same passphrase. Without a passphrase the
  backup has no secrets.
- Q: What does restore do? → A: Preview first, then apply on confirmation.

## Requirements *(mandatory)*

### Functional Requirements

**Backup**

- **FR-001**: Settings → Device MUST offer **Back up settings**, producing a downloadable file of the whole
  device configuration: every settings section the firmware has, including alerts.
- **FR-002**: The file MUST record a backup format version, the firmware version, the board/build, the
  device name and the time it was made, and MUST be readable text with the settings in the same shape as
  the settings API returns them.
- **FR-003**: Without a passphrase the file MUST NOT contain any secret (WiFi, MQTT, OTA and device
  passwords, BLE passkey, alert tokens, keys and webhook authorisation).
- **FR-004**: With a passphrase (entered twice, minimum 8 characters), the device MUST include the secrets
  encrypted with authenticated encryption under a key derived from the passphrase with a random salt and a
  deliberately slow derivation, so the secrets never leave the device unencrypted and tampering is
  detected. The passphrase is not stored anywhere.
- **FR-005**: Backup MUST require the device password when one is set (constitution VI).

**Restore**

- **FR-006**: Settings → Device MUST offer **Restore settings**: upload a backup file, optionally with its
  passphrase, and see a preview before anything is applied.
- **FR-007**: The preview MUST list, per section, every setting that will change (current → new value),
  every secret only as "will change" or "unchanged", settings kept because the backup lacks them, settings
  ignored because this firmware doesn't know them, and settings that can't apply on this board, with the
  reason.
- **FR-008**: The preview MUST say whether applying needs a restart, and warn about changes that can cut
  the owner off (WiFi network, device password, network address) or interrupt a connected imaging app.
- **FR-009**: Confirming MUST apply the restore as one settings save with the same validation as any save;
  if validation fails, nothing is applied and the reasons are shown. Cancelling MUST change nothing.
- **FR-010**: A wrong passphrase, a damaged file, a file that isn't a SQMeter backup, or one over the size
  limit MUST be refused with a reason and nothing changed. A wrong passphrase MUST NOT reveal anything about
  the secrets.
- **FR-011**: A backup with encrypted secrets restored without its passphrase MUST restore everything else
  and keep this device's current secrets, and the preview MUST say so.
- **FR-012**: Settings not available on this board (pins not broken out, absent hardware) MUST NOT be
  applied; they keep this board's values and are listed in the preview.
- **FR-013**: Restore MUST require the device password when one is set; the preview and the apply step are
  bound together so that what is applied is exactly what was previewed.

**Contract, docs, languages**

- **FR-014**: The backup and restore actions MUST be in the REST API (authenticated), the OpenAPI
  description, and the demo device (the demo produces and accepts backups without a real device).
- **FR-015**: The docs MUST replace the curl-only "Backup & Restore" section with the button flow, the file
  format, passphrase behaviour (unrecoverable if lost), cross-board restore, and the REST actions
  (constitution VII).
- **FR-016**: Every new UI string and device message MUST be added to the English catalogue with its context
  note and translated into all 13 other UI languages through the existing translation workflow.
- **FR-017**: The feature MUST stay within the resource budgets (constitution IV), including the time a
  backup or restore holds the web server (no blocking handlers; slow key derivation happens off the request
  path or within a bounded time).

### Key Entities

- **Backup file**: format version, firmware version, board/build, device name, created time, settings
  (readable), optional encrypted secrets block (salt, derivation parameters, nonce, ciphertext, tag).
- **Restore preview**: per-section changes, kept, ignored and not-applicable settings, secret status,
  restart and cut-off warnings, and a token binding it to the apply step.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A replacement device restored from an encrypted backup with its passphrase rejoins WiFi,
  reconnects to MQTT and sends alerts with no settings re-entered.
- **SC-002**: A backup made without a passphrase contains no secret value (checked by searching the file for
  each configured secret).
- **SC-003**: A wrong passphrase or damaged file never changes any setting (verified across a set of
  corrupted and wrong-passphrase files).
- **SC-004**: An owner can back up and restore in under 2 minutes without reading the docs.
- **SC-005**: A backup from a classic ESP32 restores onto an ESP32-S3 board with board-incompatible
  settings flagged and everything else applied.
- **SC-006**: Every new string appears in all 14 UI languages, and the docs and contract checks pass.

## Assumptions

- The device's existing cryptography support provides authenticated encryption and slow key derivation;
  derivation cost is chosen so a backup or restore takes a few seconds at most on the slowest board.
- File size stays within the current saved-settings and upload limits; no new storage is needed.
- Board compatibility comes from the board profiles (separate work); until those exist, pins are checked
  against the current board's valid pin set.

## Dependencies

- Spec 020 (settings dependencies), 023 (i18n), 028 (OpenAPI), the board profiles for the ESP32-S3 boards.
